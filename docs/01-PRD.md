# Lumina — Product Requirements Document (PRD)

**Status:** Draft v1.0 — 2026-10-30
**Product:** Lumina (internal system name: solo-agency client-acquisition system)
**Owner:** Mohammad Talha (solo operator)

> **Note on naming:** "Lumina" is the INTERNAL name for the system (dashboard + sending + warmup stack). The agency's client-facing brand name is **TBD** and lives only in the `brand_config` table — it is never hard-coded, and this document does not invent it.

---

## 1. Problem statement

Mohammad Talha is launching a solo service agency alongside a full-time job. He has roughly **30–45 minutes per day** to find and win clients. The problem:

- **No single place to run acquisition.** Leads live in spreadsheets, sending happens by hand (or not at all), replies sit in scattered inboxes, and follow-up sequences die from neglect. A solo operator has no sales team to cover these gaps.
- **Manual cold email does not scale and destroys deliverability.** One personal Outlook account is a single point of failure; hand-sent batches ignore per-account gaps and caps; Microsoft can lock an account for burst sending.
- **Paid sales tools are off the table for Phase 1.** The system must run on a $0 stack until client revenue pays for Phase 2.
- **Time is the binding constraint.** Anything that needs more than ~45 minutes/day, or constant context-switching between tools, will be abandoned.

**Lumina solves this** with one dashboard that owns the whole pipeline — lead → research → approved draft → queued send (with rotation, gaps, caps) → reply detection → call booking → proposal → client onboarding — while the operator spends his daily 45 minutes only on the decisions a human must make: approvals, replies, research, and calls.

## 3. Goals (measurable)

1. **G1 — Phase 0 proof:** A complete 1-test-lead loop works end-to-end (add → draft → approve → spam check → queue → send via Graph → reply detected via poll → stage moved) before any real campaign sends.
2. **G2 — 10 acceptance tests pass** before the first real campaign (see §11 for the list).
3. **G3 — Placement gate:** No sending account is eligible for campaigns until it passes the placement gate: 85%+ placement signal (AutoMailer warmup score + seed test + bounce rate), plus zero spam complaints.
4. **G4 — Daily fit:** The operator's daily routine fits in 30–45 minutes at Launch mode (5 new leads/day).
5. **G5 — First close:** First paying client within **12–16 weeks** of Phase 0 completion (warmup + sending + follow-up + calls included; this is a realistic window, not a guarantee).
6. **G6 — Zero deliverability accidents:** Bounce rate stays under 2% (target); system hard-stops before bounce exceeds 5% or spam complaints exceed 0.3%.
7. **G7 — $0 Phase 1:** Total new cash spend for Phase 1 is $0; Phase 2 (domains, mailboxes) is funded only from client revenue.

## 4. Core features

Grouped by product area. Screen names refer to the 13 finalized "Aurora Glass" (light glassmorphism) screens designed in Google Stitch; worker features refer to the Python service layer.

### 4.1 Lead management (CRM)

- **Leads Kanban** — stages: New → Researched → Contacted → Replied → Call Booked → Proposal Sent → Negotiation → Won. Separate outcomes: Lost, Disqualified, Suppressed. One company = one card (global email dedupe). Filter by campaign; Grade A first.
- **Lead Detail** — research notes (incl. auto-filled signals: PageSpeed, tech stack, booking system, reviews/ads), pain signals, timeline, AI draft (approve/edit/reject), spam-check result, send history, reply history, activities log.
- **CSV import + dedupe**; Grade A/B/C assignment via configurable per-campaign grading rules (e.g., "2+ pain signals + verified email = A").
- **Stage state machine:** stages move only forward or to an outcome, except manual human correction (logged in activities).

### 4.2 Sending engine (the core mechanics)

- **Account Manager (Accounts & Rotation screen)** — unlimited user-added Outlook accounts via **Microsoft OAuth only** (no passwords, anywhere, ever). Each account: status (`warming` / `ready` / `cooling` / `paused` / `disconnected`), warmup day, health score (0–100), today's cap, placement score, Pause/Resume. Tokens stored server-side only.
- **Send Queue** — approved emails go to a queue, never straight to send. The queue enforces: per-account 10–15 min send gap, per-account daily cap (ramp: days 15–21 → 5/day, 22–28 → 10/day, 29+ → max 20/day per personal Outlook), US-morning send window only (Mon–Fri), company-level frequency cap (no repeat to the same company within 14 days of the same campaign), and idempotency keys (no duplicate sends ever).
- **Rotation** — eligibility filter + health-score pick. New accounts must complete warmup + placement gate before becoming eligible. A paused/disconnected account is skipped; its load is NOT redistributed (duplicate risk).
- **Spam checker (3 layers):**
  1. **Pre-send:** deterministic BLOCK rules (unverified email, suppression hit, company re-contact within 14 days, >1 link / URL shortener / attachment, misleading or ALL-CAPS subject, spam-trigger wording, >120 words or >1 CTA, missing unsubscribe line or postal placeholder, unverified numbers/claims in personalization) — failed emails are blocked with the visible reason and routed back to approval. WARN rules (mild trigger word, 100–120 words, Grade B/C lead) surface for human judgment.
  2. **Seed placement test:** new account or new template is tested against the operator's own seed inboxes before scaling.
  3. **Post-send monitoring:** hard bounce → suppress; 3× soft bounce → suppress; unsubscribe/complaint → global suppression on ALL accounts + instant sequence stop; 7-day bounce >2% = warning, >5% = system stop; spam complaint >0.1% = warning, >0.3% = system stop.
- **Kill-switch** — one click stops all sending; pending queue items do not fire.
- **Compliance built in:** global suppression list, unsubscribe footer line + postal address placeholder (from `brand_config`), opt-out honoured within 10 days, plain-text emails (no tracking pixel), audit log of every sent email (exact text + approved-by + timestamp, immutable).

### 4.3 Reply detection & inbox

- **Poll Worker** — checks each account's inbox every 15 minutes, **staggered** per account (Account 1 at :00, Account 2 at :03, …) to avoid Graph throttling.
- **Thread-first matching:** replies are matched to the lead by conversation/thread ID first, sender email second. Out-of-office/auto-replies are classified as such and never treated as "Replied."
- **Replies Inbox** — all accounts' replies in one place. Classification: Positive / Busy / Price / Not Interested / Referral / Out-of-office / Bounce / Unsubscribe. Positives pinned to the top. Stop-on-reply fires on every account the moment a reply lands.
- **Reply continuity:** each reply's `reply_from_account_id` = the original sending account (auto-selected; manual change shows a warning).
- **AI classification** (Gemini/Groq) is Phase 2; the scaffold classifies by sender match with human review on negatives.

### 4.4 Campaigns (niche-flexible by design)

- **Campaign = the whole niche in one data record:** ICP definition (incl. negative filters), research checklist, pain taxonomy, grading rules, enrichment config, email templates + variables (Day 0/3/7/12 + Day-5 manual LinkedIn touch), sequence timing, offer + pricing, discovery questions, proposal template, onboarding checklist, extra spam rules.
- **The system never knows a niche's name:** no niche is hard-coded anywhere. New niche = new campaign record, 15 minutes, zero code.
- **Template library presets:** dental / law / shopify / hvac / blank, plus cloning an existing campaign.
- **Campaign switcher + comparison view:** all screens filter by campaign; one screen compares reply rate / meeting rate across campaigns.
- **Launch-mode guardrail:** only one campaign may be active at a time; activating a second shows a warning (time doubles or both slow down).
- **Sequences:** per-campaign Day 0 / 3 / 7 / 12 templates, stop-on-reply, per-campaign checklist.

### 4.5 Calls, proposals, clients

- **Calls** — Cal.com bookings, 24h + 1h reminders, no-show reschedule task, call prep brief, ROI calculator (tickets/week × minutes × hourly cost).
- **Proposals & Clients** — 1-page proposal draft per campaign template; contract module (SOW: scope, 2 revisions, extra $50/hour, ownership transfers only on full payment; e-signature option); onboarding checklist; **payments:** Payoneer/Wise invoices, payment links/status, 50%/50% tracking, overdue reminders, 50% advance verified before work starts.
- **Unsubscribe page + data deletion** — footer line leads to a confirmation page with reason capture, suppression timestamp, and a data-delete request task.

### 4.6 Health & warmup monitoring

- **Deliverability Health** — per-account and system-level bounce / reply / placement / spam-complaint rates, weekly trends, next week's cap suggestion, AutoMailer warmup score + seed-test results, daily snapshot replacing any manual log.
- **Warmup Monitor** — every account's warmup day, tasks (normal emails to known contacts + AutoMailer warmup network), placement test results. New accounts start `warming`, never `ready`.
- **Circuit breaker:** an account that breaches hard thresholds auto-pauses or cools; the rest of the system keeps running.

### 4.7 Settings & brand

- **Settings & Brand** — agency name (TBD), founder name, postal address placeholder, Cal.com link, LinkedIn headline, send window, caps. One change propagates to every template. Alerts: dashboard inbox + self-email via Graph (no Telegram). **Home — Command Center:** today's 5 tasks, KPIs (leads, sent, reply rate, calls, proposals, won, system health), kill-switch.
- **Mobile dashboard:** approvals and positive replies handled from the phone; alerts link straight into the approval.

## 5. MVP scope

**IN (first shippable system):**

1. **Phase 0 proof gate** — Azure app + delegated Graph permissions (Mail.Send, Mail.Read) + 1 Outlook account OAuth + 1 test send + 1 test poll + 1 test lead's full loop. Nothing else starts until this passes.
2. **Data foundation** — Supabase project with migration 0001 (19 tables, RLS `lumina_owner_all`, idempotent), brand_config seed, campaign template presets.
3. **Core dashboard** — Leads Kanban + Lead Detail + CSV import + dedupe + grading; brand_config.
4. **Queue + rotation + spam** — send_queue with idempotency, rotation pick (eligibility + health score), per-account gap/cap, Layer-1 spam checker, global suppression, kill-switch.
5. **Poll + Replies Inbox** — staggered 15-min polling, thread-first then sender matching, stop-on-reply, Replies Inbox with classification, Cal.com booking link.
6. **First campaign** — one active campaign (niche TBD, see §8), Day 0/3/7/12 sequence, Launch-mode guardrail, first 100 emails human-approved (no auto-send).
7. **Health basics** — daily account health snapshot, auto-pause on hard breaches, placement-gate check before any account goes `ready`.
8. **Audit + export** — immutable send audit log, weekly leads export.

**IN but minimal:** payments tracking (invoice/status/50-50), unsubscribe page, call reminders, automated research signals (PageSpeed/tech/reviews auto-fill, human verifies).

**Current build status (honest):** The hybrid worker scaffold exists — Supabase migration 0001 (19 tables, RLS, seeds), Python FastAPI worker (services: rotation, spamcheck, graph, health, notify; workers: send, poll, health) with **18/18 tests passing**. Known scaffold limits: tokens are read from env var names (Supabase Vault in production); poll matching is sender-email only (thread-first matching is Phase 2); AI draft/classification is Phase 2. Phase 0 requires the operator's own Supabase project, Azure app, and Outlook OAuth — these are user actions, never credentials in chat.

## 6. User stories

1. **As a solo operator, I want** to add my own Outlook accounts via OAuth (no passwords), **so that** a single account lock can never take down my whole pipeline.
2. **As a solo operator, I want** approved emails to enter a queue that enforces gaps, caps, and send windows automatically, **so that** I never have to think about spacing or accidentally burst-send.
3. **As a solo operator, I want** every email spam-checked before sending with the exact block reason visible, **so that** I fix the copy instead of discovering the problem in the spam folder.
4. **As a solo operator, I want** replies detected across all accounts in one inbox, pinned positives first, with sequences stopping automatically, **so that** I never send an embarrassing follow-up to someone who already replied.
5. **As a solo operator, I want** my 5 daily leads researched today for tomorrow's batch, **so that** my routine fits in 30–45 minutes without skipping research.
6. **As a solo operator, I want** the first 100 emails to require my explicit approval each, **so that** the system earns my trust before anything runs hands-off.
7. **As a solo operator, I want** one click to stop all sending, **so that** I can react to a deliverability scare in seconds, not hours.
8. **As a solo operator, I want** to switch niches by cloning a campaign and editing its data, **so that** a new niche takes 15 minutes, not a rebuild.
9. **As a solo operator, I want** per-account health scores and weekly trends in one place, **so that** I make cap/volume decisions from data, not gut feeling.
10. **As a solo operator, I want** payments, proposals, and onboarding in the same dashboard, **so that** no client step happens in a forgotten spreadsheet.

## 8. Assumptions

1. Microsoft Graph works with the operator's personal Outlook accounts via delegated permissions (Mail.Send, Mail.Read) — to be proven in Phase 0.
2. The operator owns the accounts he adds (real names, real owners; never his job account or main personal account).
3. The free tiers listed in the stack doc (Supabase Free, Vercel Hobby, Apollo/Hunter free, MillionVerifier 100 credits one-time, AutoMailer free warmup, Gemini/Groq free) remain available at signup; limits are re-checked on each signup.
4. Verification supply is limited: MillionVerifier's 100 credits are one-time, not monthly — only verified leads enter the queue, so early volume is capped by verification supply until paid credits are budgeted.
5. Tue–Thu US-morning sending performs best; the queue prefers those windows.
6. Personalization must be genuine and research-based (template + real observation per lead); rotation does not fix bad lists or spammy copy.

## 9. Risks (with mitigations)

| # | Risk | Mitigation |
|---|---|---|
| R1 | **Microsoft locks a sending account** for cold outreach | Multi-account rotation from day one; per-account caps/gaps; circuit breaker auto-pauses the account; system keeps running on the rest. Never use job/main personal account. |
| R2 | **Graph setup fails on personal accounts** (consent, permissions) | Phase 0 proof gate exists exactly for this — no downstream build is committed until it passes. |
| R3 | **Token expiry/disconnect breaks polling** | Token refresh failure → account marked `disconnected` + reconnect alert; queue skips the account; pending emails are NOT redistributed (duplicate risk); no passwords anywhere. |
| R4 | **Reply misclassification** (out-of-office, bounce, team reply) | Thread-first then sender matching; auto-replies never count as "Replied"; negatives/unsubscribes go to human review. |
| R5 | **Free-tier limits choke the system** (Supabase rows/invocations, Apollo credits, Gemini rate limits) | Monitor usage on the Health page; cron polling staggered (not one 15-min Edge Function blast); paid upgrades only when a limit actually blocks work, never pre-emptively. |
| R6 | **Verification credit gap** (100 one-time credits vs 500-email funnel) | Only verified leads queue; paid verification is a separate budgeted line once the 100 are used. No "verified list" claims without credits. |
| R7 | **Operator runs out of time** (job pressure) | Launch mode = 5 leads/day + one active campaign guardrail; research pre-batches for tomorrow; mobile approvals; kill-switch for bad weeks. |
| R8 | **CAN-SPAM non-compliance** | Global suppression list, unsubscribe footer + confirmation page, postal address placeholder, 10-day opt-out honouring, no full email bodies in alerts, minimum lead data sent to AI providers. |
| R9 | **Optimistic timeline** (60-day close) | Revised to 12–16 weeks with honest funnel math (25% proposal→close, not 50–100%); the plan states this is a window, not a promise. |

## 10. Out-of-scope features (explicit)

1. **Multiple active campaigns in Launch mode** — supported by the system, but the guardrail limits the operator to one; multi-campaign is Scale mode.
2. **Tracking pixels / open tracking** — removed by design; emails are plain text.
3. **HTML-heavy emails, images, attachments** — not in Phase 1.
4. **AI-generated drafts without human approval** — the first 100 emails are human-approved, always; AI is a drafting assistant, never the sender.
5. **Automated LinkedIn outreach** — the Day-5 LinkedIn touch is manual; no LinkedIn bots.
6. **Purchased or scraped-unverified lists** — only verified leads enter the queue.
7. **SMS / cold-call automation** — not in this system.
8. **Multi-user / team seats** — single owner only (RLS `lumina_owner_all`).
9. **Telegram or any paid alert channel** — alerts are dashboard inbox + self-email only.
10. **Phase 2 items:** sending domains + M365 inboxes (25–30/day caps), AI classification, thread-first poll matching (scaffold does sender match), paid verification budget, Vault-backed token storage, agency multi-helper access.

## 11. Acceptance criteria

**Gate 1 — Phase 0 proof (before any further build):**
- Azure app + 1 Outlook account connected via OAuth (no passwords)
- 1 test send via Graph succeeds
- 1 test poll via Graph detects the reply
- 1 test lead completes the full loop with zero campaign machinery

**Gate 2 — 10 acceptance tests (before the first real campaign):**
1. Spam-check fail → no send; the reason is visible on the Lead Detail screen.
2. Suppressed lead → no send, from any account.
3. Paused account → queue skips it; its load is NOT redistributed to other accounts.
4. Duplicate send attempt → idempotency key blocks it.
5. Token expiry → account marked `disconnected` + operator alerted; the system does not crash.
6. Reply received → sequence stops on all accounts; lead moves to Replied.
7. Bounce spike → account/system auto-pauses with a clear warning.
8. Kill-switch → all pending sends stop within one poll cycle.
9. Agency name change → every template reflects it with one edit.
10. Campaign switch → the second campaign's checklist/templates apply; the first campaign's copy does not mix in.

**Gate 3 — Placement gate (before any account joins a campaign):**
- 85%+ placement signal (AutoMailer warmup score + seed test + bounce rate)
- Zero spam complaints
- Account status flips from `warming` to `ready` only after both hold

**Pre-campaign gate — trust assets:** brand config complete (agency name still TBD — see §9 of the open decisions below), demo asset ready, Cal.com link live. The queue does not start without these.
